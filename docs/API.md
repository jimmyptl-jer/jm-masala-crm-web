# API (milestone 1)

The CRM API lives in `api/` (Express 5, TypeScript, MongoDB with the official driver, plain TypeScript input checks). It is being built
endpoint by endpoint, buyers and quotes first. Base path `/api/v1`; `GET /health` is outside it.

## Code layout
The API is organised as MVC per feature: model (document type only), service (database queries and rules), view (JSON presenter), controller (request in,
view out), routes (URL wiring) and validator (plain functions, no schema library). Buyers (full CRUD), inquiries (full CRUD), products and quotes use it already; auth follows. Quotes are live: list, detail, calculate, draft, issue, PDF, send, status, follow-up, activities and the dashboard (revise, duplicate and delete draft are not built). The full description is
in `api/README.md`.

| Add or deactivate a CRM user | create their account in Supabase (Authentication > Users, Auto Confirm User), then `npm run add-user -- <email> "<Full name>" <admin\|sales>`; stop someone with `npm run add-user -- <email> --deactivate` |
| Bring the database in line with the product catalogue | `npm run seed:products`: renames the old "Psyllium" everywhere, sets categories on existing products and adds every catalogue product without a record as a **draft** (no GST %, HS code, grade, specification or price; unit MT). Safe to repeat; never deletes or overwrites |
| Load sample buyers, inquiries and quotes | `npm run seed:demo` (into the configured, empty database) |
| Load the proposed product grades | `npm run seed:grades` shows a dry run (nothing written); `npm run seed:grades -- --commit` writes 55 **draft** product records (one per grade of the 13 catalogue products, each with its `product_code` such as `SPC-CUM` and its list of packaging options; the data is in `api/scripts/grade-catalogue.ts`). Purity, moisture, specification, HS / HSN, GST % and prices stay empty and every record is a draft, so none can be quoted until someone checks it and activates it in Products. The only quality field set is `cleaning`, and only where the grade name says Machine or Sortex. Existing name + grade pairs are never changed (safe to run again), and older records of those products get the code if they had none. The proposal's "Custom ..." lines are not seeded |
| Checks | `npm run typecheck`, `npm test` (one in-memory MongoDB for the whole run, started in `test/helpers/global-setup.ts`; each test file gets its own database `jm_test_<random>` that its harness drops at the end; first run downloads a `mongod`), `npm run build` |

Environment variables: `PORT` (3000), `MONGODB_URI` (Atlas connection string), `MONGODB_DB` (`jm_masala_crm`), `SUPABASE_URL`
(your project URL, required, public), `CORS_ORIGINS` (comma separated web origins, default `http://localhost:5173`; exact addresses, or a subdomain pattern `https://*.example.com` (https only, a full domain after the `*`, matches subdomains but not the bare domain; a bare `*` is always refused), and in production the variable must be set), `PUBLIC_API_URL` (optional, the https address of this API such as `https://api.example.com`: links that leave the API, like the 30 day PDF link in an e-mail, are built from it instead of the request's `Host` header, which a caller can forge; in production a missing value is a start-up warning; helper `publicApiUrl()` in `src/services/public-url.ts`), `TRUST_PROXY` (how many reverse proxies sit in front: a number, `false`, or a list of trusted addresses; default `1` in production and off elsewhere; it decides which address the rate limits see), and in production `SUPABASE_URL` must be https. For
`ADMIN_EMAIL` (the one address allowed to create the first administrator on the setup page, also used by `seed:admin`; leave it out to switch the setup page off), `ADMIN_NAME` (`seed:admin` only). `SMTP_USER` and `SMTP_PASS` (Gmail address and a Google **app password**, set both or neither; see E-mail below), `MAIL_COPY_TO` (optional, comma separated: addresses that get a hidden bcc copy of every quotation e-mail; the buyer never sees them and is not copied twice), `MAIL_FROM_NAME` (sender name, default `Jimmy Patel - JM Masala trading LLP`), `CHROME_PATH` (Chrome / Chromium for the PDFs; empty = look in the usual places) `PDF_LINK_SECRET` (32+ random characters that sign the 30 day PDF links; empty = links off) `S3_BUCKET`, `S3_REGION` (default `ap-south-1`), `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_ENDPOINT` and `S3_FORCE_PATH_STYLE` (file storage, see Storage; set the bucket and both keys together or none), and `LOG_LEVEL` (debug, info, warn, error, silent; default info; see Logging). Apart from the SMTP app password there is no password or signing secret in the API's configuration. `.env` is git-ignored; never commit it, and keep `.env.example` free of real values.

## Auth
Sign-in, sign-out, password reset and e-mail confirmation are done by **Supabase Auth** in the web app (`@supabase/supabase-js`).
The API has no login route and stores no passwords.
- Every route except `GET /health` needs `Authorization: Bearer <Supabase access token>`. The API checks the token's signature against
  the project's public signing keys (`<SUPABASE_URL>/auth/v1/.well-known/jwks.json`, ES256 or RS256; the keys are refreshed after an hour, and when a refresh fails the old keys keep working, with one background retry at most every 30 seconds, for at most 24 hours), its expiry,
  its issuer (`<SUPABASE_URL>/auth/v1`) and audience (`authenticated`). Tokens signed with the legacy shared JWT secret (HS256) are
  not accepted: use the project's asymmetric signing keys. An invalid or missing token is 401 `unauthorized`.
- Who may use the CRM is decided by our `users` collection (email unique without case, `auth_id` = Supabase user id, `role` `admin`
  or `sales`, `active`), never by the token. An administrator adds the person (Supabase account in the dashboard, then the CRM user);
  on the person's first sign-in the API links the two by e-mail address (once: a second Supabase account with the same e-mail
  cannot take over). **Linking needs a confirmed e-mail address:** the token must carry `email_verified: true` (or `user_metadata.email_verified: true`); otherwise the call is 403 `email_not_verified` and nothing is linked (the same holds for `POST /signup/request` when it would link a person an administrator added, and for `POST /setup/claim-admin`). Keep **e-mail confirmation on** in Supabase and **sign-ups off**, otherwise anyone could claim an address.
- **Sign-up and onboarding:** new people create their own account on the public page `/sign-up` (Supabase sign-up; needs "Allow new users to
  sign up" on in Supabase). That gives no access: the web app then calls `POST /signup/request`, which records them as a pending `sales`
  user, and every route answers 403 `account_inactive` ("waiting for approval") until an administrator approves them in
  Settings > Users (`PATCH /users/:id { active: true }`). A valid Supabase sign-in for someone the CRM does not know yet is 403
  `forbidden`; the web app answers that with the sign-up request automatically. Keep e-mail confirmation on. Role and `active` are read from the database on every request, so
  deactivating someone takes effect at once. The last active administrator can never be deactivated or demoted.
- **First administrator:** the web app has a public setup page at `/jm-masala-crm-create-admin-user` (`web/src/pages/CreateAdmin.tsx`). The owner signs up (or signs in) with Supabase there and claims the administrator account through `POST /setup/claim-admin`. The hidden address is not the protection: the API allows it only for the `ADMIN_EMAIL` address, only while no active administrator exists, and only once (an atomic marker in `counters`, removed again if creating the administrator fails, so setup can be tried again); the address must also be confirmed in Supabase (403 `email_not_verified`). Afterwards the page only says setup is done. `npm run seed:admin` / `npm run add-user` do the same from the command line.
- `requireAdmin` guards writes to products (and later settings and users). There is no bypass mode and no demo login.

## E-mail
The API sends e-mail through one mailer (`src/services/mailer.ts`, Gmail SMTP on `smtp.gmail.com:465` with an app password: turn on 2-Step Verification, then Google Account > Security > App passwords). Every service that sends mail takes this mailer; none talks to Gmail itself, and the web app never sees the credentials. With `SMTP_USER` / `SMTP_PASS` unset, mail is skipped and a "email skipped" line is logged (local development and tests). Notification mail is plain text, sent in the background: a Gmail failure is logged (subject and error only) and never fails the request. The quotation e-mail is different: the user is waiting for it, so a failure is reported (502 `send_failed`) and nothing is logged on the quote. Gmail always sends from `SMTP_USER` (`MAIL_FROM_NAME` is the name beside it) and a personal account allows about 500 e-mails a day.
| Trigger | Recipients | Subject |
|---|---|---|
| `POST /signup/request` creates a pending user (not on a repeat) | every active administrator | `Access request: <name>` |
| `PATCH /users/:id` with `active: true` on someone who was not active | that person | `Your JM Masala CRM access is approved` |

## Logging
The API writes **one JSON object per line** to the standard output (warnings and errors to the error output), which Docker, the server journal and every log service already collect. Every line has `ts` (ISO time), `level` and `msg`, plus named fields. Code: `src/logger.ts` (`log.debug / info / warn / error`, `log.audit`). `LOG_LEVEL` in `api/.env` is `debug`, `info` (default), `warn`, `error` or `silent` (silent in tests).

| What | Level | Fields |
|---|---|---|
| Every request, one line when it ends | info; **warn** for 4xx (every refused sign-in and permission check, with `code`), **error** for 5xx, **warn** `slow request` over 3 s; `/health` only at debug | `id` (also the `X-Request-Id` header, which the web app can read), `method`, `path` (no query string; the signed PDF link's token is replaced by `:token`), `status`, `ms`, `user`, `ip`, `code` |
| An unhandled error (the caller gets only a generic 500 and the `X-Request-Id`) | error | `id`, `method`, `path`, `user`, `error`, `stack` |
| Start-up, database connected, listening, shutting down, unhandled rejection, uncaught exception | info / error | which optional features are on (e-mail, PDF, share links, setup page); never a secret value. A missing Chrome or SMTP login is a **warn** |
| E-mail sent / skipped / failed | info / info / error | `subject`, number of recipients, their **domains** (never the addresses), attachment count, `ms` |
| PDF made, PDF failed, quote e-mail failed | info / error / error | `quote`, `number`, `revision`, `bytes`, `ms`, `error`, `stack` |
| **Audit events** (`audit: true`, `event: ...`): `quote.draft_created`, `quote.issued`, `quote.emailed`, `fx.changed`, `settings.changed`, `user.access_requested`, `user.updated`, `setup.admin_claimed`, `product.created`, `product.updated`, `product.rates_changed`, `product.daily_rates_changed`, `product.archived`, `product.deleted`, `partner.created`, `partner.updated`, `partner.archived`, `buyer.created`, `buyer.updated`, `buyer.archived`, `inquiry.created`, `inquiry.updated`, `inquiry.archived` | info | who (`user` = CRM user id), what (ids, number, total, old and new dollar rate, which fields changed) and the `request` id |

**Never in a log:** passwords, tokens, keys, connection strings, bank details, cost and margin. Error text is scrubbed too: the user name and password inside any `scheme://user:pass@host` address (MongoDB, SMTP ...) in an error message or stack are replaced by `[redacted]`. Any field whose *name* looks like one is replaced by `[redacted]` at any depth (`redact()` in `logger.ts`), long text is cut at 300 characters, lists at 20 items, depth at 4, and e-mail addresses appear only as `@domain`. To find what happened to a user's request, search the log for its `X-Request-Id`; to see who did what to a quote, filter `audit: true` and the quote id.

## Quote calculator and the dollar rate
All money maths is in `src/services/quote-calc.ts` (decimal.js, half-up to 2 places; nothing is ever calculated in the web app). Line amount = quantity x rate. A bill-level discount (a money amount) is shared over the lines in proportion to their amounts, so GST is charged on the discounted value. **Export:** no GST; freight and insurance count only for CFR / CIF; total = amounts - discount + freight + insurance. **Domestic:** GST per line from the product's rate; buyer state code = company state code gives CGST + SGST (half each), a different one gives IGST (a missing code assumes same state and adds a warning); the total is rounded to the whole rupee and the difference is `round_off`. **Dollar rate:** with today's rate (`GET /fx-rate`) a USD quote also reports its total in rupees and an INR quote its total in dollars (`equivalent: { currency, amount, rate }`); EUR, GBP and AED have none. The rate only adds this second figure, it never changes the amounts. **Margin (administrators only, never printed):** per line (rate - cost) x quantity; total = sum of the lines that have a cost minus the discount; percent of the taxable value. The cost is in rupees per unit: on a USD quote it is converted at the dollar rate (no rate = no margin, with a warning), on an INR quote it is used as it is, and on EUR, GBP and AED quotes **no margin is worked out** (`margin.total` null, with a warning) because no rate to those currencies is held. When a discount is given and some lines have no cost, the total and percent are null (the discount is shared over every line, so a partial total would be wrong); the per-line margins are still returned, and `complete` stays true only when every line has a cost. **Who sees it:** only an `admin`. For anyone else the `cost_rate` and `margin` keys are absent from every quote answer, `POST /quotes/calculate` returns an empty margin (`total` and `pct` null, `complete` false) and no margin warnings, and sending a `cost_rate` is refused with 403 `forbidden`. A non-admin saving a draft keeps the costs an admin entered (matched by line position and product). **Stale dollar rate:** when the saved rate is not from today it is still used, and a warning `The dollar rate is from <date>, not today...` is added on calculate, draft save and issue (USD and INR quotes); issue is never blocked. **Size limit:** the products total of one quote may not exceed 900,000,000,000 (400 on `lines`), so the figures and the amount in words stay exact. Amount in words follows the currency (US Dollars, Euros, Pounds Sterling, UAE Dirhams, Rupees with lakh / crore grouping).

## Quotation flow (everything is done by the API; the web app only displays)
1. **Create quote** (`POST /quotes`, or `PUT /quotes/:id/draft` to change it): the form values go to the API, which checks them, applies defaults from the buyer and Settings, calculates every figure (see above) and saves the draft. The answer is the `QuoteDetail` **plus `document`**: `{ revision, draft: true, html, email }`. `html` is the finished quotation page in the JM Masala letterhead format (the same layout as the PDF, marked "DRAFT FOR REVIEW", shown in a frame as is; its letterhead images are linked from `GET /assets/letterhead/:file`, which needs no login). `email` is the message Send will deliver: `{ to, subject, text, html }`. `GET /quotes/:id/revisions/:rev/document` returns the same for any draft or issued revision. Cost and margin are never in either.
2. **Verify**: the user looks at the page and the e-mail. To change something they save the draft again and the page is redrawn.
3. **Send** (the web app's Issue and send): `POST /quotes/:id/issue` numbers it (`JM/Q/001/2026-27`, a counter per April to March financial year), freezes a snapshot of company, bank (export only) and buyer, fixes the dollar rate used, sets Sent, validity and follow-up, and makes the **PDF** (`src/services/pdf.ts`: the same page with the images embedded, printed by the Chrome / Chromium on the machine through puppeteer-core; set `CHROME_PATH` in Docker). A PDF that fails does not undo the issue (`pdf.status: 'failed'`; `POST /quotes/:id/revisions/:rev/render` retries). **Issuing without transactions** (a standalone MongoDB has none): (1) one `findOneAndUpdate` *claims* the open draft by setting `issuing_at`; while a claim younger than 60 seconds exists, a save of the draft or a second issue gets 409 `conflict`; (2) the figures are recalculated from the document the claim returned; (3) the quote number is taken only now, after everything that can fail, and handed back if the commit fails; (4) one `findOneAndUpdate`, filtered on the claim and the `draft_version`, writes the issued revision, number, status and dates and clears the claim. A save (`PUT /quotes/:id/draft`) also needs the `draft_version` it read, so two saves at once, or a save against a draft that was just issued, give 409 `conflict` instead of one overwriting the other. **Remaining gap:** a crash between taking the number and the commit leaves one number unused (a gap in the sequence); the claim expires after 60 seconds and the draft can be issued again. A quote left as issued-with-a-draft-revision by an earlier version is recovered the same way. Issue, render and send are limited to 40 requests a minute per signed-in user (429 `rate_limited`), and at most two pages are rendered by Chrome at once (the rest wait). Then `POST /quotes/:id/revisions/:rev/send { channel: 'email', note? }` e-mails the PDF to the buyer and logs an `email` activity (a failure to write that log is only logged on the server, it never turns a sent mail into an error). A second send of the same revision to the same address within 30 seconds is refused with 409 `already_sent` (the guard is kept on the quote, `send_lock`, and is released at once when the send fails). WhatsApp cannot be sent by the server (400): the web app opens it from the signed link.
4. **The quotation e-mail** (`src/services/quote-send.service.ts`, text and HTML): "Dear <contact or company>", greeting from the company, the product names, the standard Terms & Conditions and Sample Policy, the closing paragraphs, the signature (Export Sales Team, company, address, e-mail | phone, website, all from Settings) and the confidentiality notice. An optional `note` is added as a paragraph after the introduction. Replies go to the sender's own address (`Reply-To`). Subject: `Quotation <number> - <company>`.
5. **Share link**: `GET /quotes/:id/revisions/:rev/pdf?json=1` gives `{ url, expires_at }`, a link valid 30 days that opens the PDF without a login (`GET /files/quote-pdf/:token`, HMAC signed with `PDF_LINK_SECRET`; 503 `links_off` when the secret is not set). Without `json=1` the same route returns the PDF itself.
Terms printed on the PDF are the quote's own list when it has one, else the standard clauses (`src/services/quote-terms.ts`, the same wording as `web/src/lib/quoteTerms.ts`; keep the two in step). Fonts: the page asks for Cormorant Garamond and Lato and falls back to Georgia and Segoe UI / Arial when they are not installed on the server.

## Storage (S3)
With `S3_BUCKET` set (a private bucket on Amazon S3 or an S3-compatible service; the code is the first version's `s3.ts`, brought back as `services/storage.ts`) the API keeps two kinds of files there:
- **Quotation PDFs**: `pdfs/<quote number>/revision-<n>.pdf` (for example `pdfs/JM-Q-005-2026-27/revision-0.pdf`), written when a quotation is issued or its PDF is remade. If the upload fails, the PDF is kept in MongoDB (`quote_pdfs`) so issuing never breaks, and the log says so. Reading looks in S3 first and then in MongoDB, so PDFs made before S3 was switched on are still served. The bucket is never public: a PDF is opened through the signed-in route or the signed 30 day link.
- **Daily rates**: every time a rate is set (the Daily rates tab, the product form, `PUT /daily-rates`) the day's whole price list is written to `daily-rates/DD-MM-YYYY.json` (for example `daily-rates/30-10-2025.json`): every active grade grouped by product with its USD and INR rate per kg after the change, who saved it and when. A later change on the same day replaces the file, so the file of a date holds that day's last state. A storage outage is logged and never fails the save (the rates are already in the database and in `rate_history`).

Without `S3_BUCKET` PDFs stay in MongoDB and no rates file is written. The keys are secrets: they live only in `api/.env` / the real environment and never leave the API.

## Errors
Every failure is `{ "error": { "code", "message", "fields"? } }`. `fields` maps an input name (dotted for nested) to a message.
Codes so far: `validation_error` (400), `invalid_json` (400), `payload_too_large` (413, body over 1 MB), `unsupported_media_type` (415) and the other 4xx errors that middleware raises keep their own status (`bad_request`, `request_timeout` ...) with a generic message, `email_not_verified` (403), `daily_rates_partial` (500, with `saved` and `not_saved` grade ids), `unauthorized` / `invalid_credentials` (401), `forbidden` (403),
`not_found` (404), `duplicate_product` / `duplicate_buyer` (409), `internal_error` (500, generic text; details only in the server log with the request id).

## Security notes (audit fixes)
- **E-mail confirmation:** see Auth. Linking by e-mail, the sign-up request that would link, and the first-administrator claim need `email_verified`.
- **Public PDF links:** a link is `<payload>.<signature>`; the payload may carry a per-quote `link_nonce` (stored on the quote; absent until the first revoke, so links made before that stay valid). `revokePdfLinks(d, quoteId)` in `src/services/quote-pdf.service.ts` stores a new nonce, which stops every link made before; links are made with `currentLinkNonce()` + `signPdfToken(..., nonce)` and opened only when `pdfLinkStillValid()` agrees. The route that calls `revokePdfLinks` (a `POST /quotes/:id/revoke-links`) belongs with the quote routes.
- **Links that leave the API** (e-mail, preview) should use `publicApiUrl(config, req)` (`PUBLIC_API_URL`, else the request host), never `req.get('host')` directly.
- **Rate limits:** `/setup/status`, `/setup/claim-admin` and `/signup/request` each have their own counter (30 per 15 minutes per client address); the general limit is 300 per minute. Which address is "the client" depends on `TRUST_PROXY`.
- **Concurrent edits:** buyer, partner and inquiry changes write only the fields that changed (`$set`), so a contact logged at the same moment is not lost. Deleting a product grade checks that no quote used it and then deletes; a quote could in theory start using the grade between the two steps (accepted: a quote keeps its own frozen copy of the grade; `quotes.product_ids` is indexed so the check is fast).
- **Last administrator:** the check is made before and again after the write; if two administrators demote each other at the same moment, the change is rolled back and 409 `last_admin` is answered.

Response shapes match `web/src/lib/types.ts` (`Me`, `Buyer`, `QuoteListRow`, `Product`): snake_case, string ids, ISO dates,
money as decimal strings. `image_url` on products is `null` until the image routes exist.

## Data model (MongoDB)
- `rate_history` (one row per grade per day: `product_id`, `date`, `ref_rate_usd`, `ref_rate_inr`, `set_by_name`; unique on product and date), `users`, `buyers`, `inquiries`, `samples`, `price_sheets` (dated price calculator sheets: inputs, results and who saved them), `products`, `partners` (contacts, services with documents and activities embedded; `partner` counter), `quotes` collections plus `counters` (running numbers; `buyer`, `inquiry` and `sample` hold the last code). A quote may carry `inquiry_id` (checked when the quote is created) and `GET /quotes` accepts `inquiry_id`; buyers created before codes existed get one at start-up (oldest first); `_id` is an ObjectId, exposed as the string `id`.
- `quotes` holds the summary fields the list needs (`status`, `number`, `grand_total`, `products`, `product_ids`, `activity_at`,
  `activity_date`) and, inside the same document, `revisions[]` (each with its lines, terms, figures, `usd_inr_rate`, `pdf_ready` and, once issued, the frozen `snapshot`) and `activities[]`. Saving or issuing keeps the summary fields in step. Control fields: `draft_version` (counts saves of the open draft), `issuing_at` (set while an issue holds the draft), `status_changed_at` (the Won and Lost counts of the dashboard) and `send_lock` (the 30 second send guard). An issued revision is never rewritten by the draft routes (they require `latest_state: 'draft'` in the update filter; MongoDB has no triggers).
  Quotes seeded before revisions existed have none and show an empty revision list. `settings` (one document, `_id: 'company'`), `fx_rates` (`_id: 'usd_inr'`: `rate`, `rate_date`, `updated_by_name`) and `quote_pdfs` (`<quote id>:<revision>` -> the PDF bytes) are the other collections.
- Numbering follows `docs/DOMAIN-SPEC.md` (`JM/Q/001/2026-27`; the financial year is written `2099-2100` across a century), taken from a counter document updated atomically
  (`findOneAndUpdate` with `$inc`) when a quote is issued, as late as possible and handed back if the issue fails.
- Indexes are created on start-up (`ensureIndexes` in `api/src/db.ts`).

## Web app: mixed mode
Set `VITE_API_URL=http://localhost:3000/api/v1`, `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` (the same Supabase project as `SUPABASE_URL` in `api/.env`), and leave `VITE_AUTH_BYPASS` unset (or not `true`), in `web/.env`.
The web app sends the signed-in person's Supabase access token with every live call. The calls in `LIVE_ROUTES` (`web/src/lib/config.ts`) go to the real API: `/me`, buyers (list, one, create, update), `GET /buyers/summary`, `POST /buyers/:id/activities`, inquiries, samples, the admin-only price calculator and its saved sheets (`/price-calculator`), partners (including `/partners/:id/activities`), products, `GET /products/:id/rate-history`, `PUT /daily-rates`, users, `GET /team`, setup, `GET /settings`, `PUT /settings`, `/fx-rate`, `/send-channels`, `GET /dashboard`, and for quotes: `GET /quotes`, `POST /quotes/calculate`, `POST /quotes`, `GET /quotes/:id`, `PUT /quotes/:id/draft`, `POST /quotes/:id/issue`, `PATCH /quotes/:id/status`, `PATCH /quotes/:id/followup`, `POST /quotes/:id/activities`, and `/quotes/:id/revisions/:rev/{pdf,render,send,document}`. **Live mode never falls back to sample data:** when `VITE_API_URL` is set, any call not in `LIVE_ROUTES` fails with `ApiError(501, 'not_available', 'This is not available yet')`, and the screens hide the controls whose route is not live (`hasRoute()` in `config.ts`): quote Revise, Duplicate and Delete draft, price-hint chips, product image upload/remove, logo upload, the Excel import, the quotation Export, and anything else not listed above. Adding a route to `LIVE_ROUTES` turns its control on. Sample-data mode (`VITE_API_URL` empty, development or an explicit `VITE_DEMO=true` build) answers every call from the in-memory sample data; a production build without `VITE_API_URL` fails unless `VITE_DEMO=true`. The quote form (`web/src/pages/QuoteForm.tsx`) saves with the real API and its Preview shows the page and e-mail the API made (`web/src/components/quoteform/ApiQuotePreview.tsx`); the dashboard's first box (`web/src/components/FxRateBar.tsx`) is today's dollar rate. List screens that read `GET /quotes?limit=100` (Today, Pipeline, Follow-ups, Orders) show a notice when the API's `total` is larger than the rows received. Restart the web dev server after changing `.env`.
